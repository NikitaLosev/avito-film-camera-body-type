# EDA и описание данных

Проект: автоматическое определение типа корпуса плёночной камеры по объявлению Авито.
Категория: Электроника / Фототехника / Плёночные фотоаппараты.
Целевой атрибут: `film_camera_body_type`.
Папка этапа: `eda/`.

Ноутбук с EDA: [`eda.ipynb`](./eda.ipynb).

Если смотреть из корня репозитория, путь к нему будет `eda/eda.ipynb`. Сам ноутбук лучше запускать из папки `eda/`, потому что пути внутри него считаются от `Path.cwd().parent`.

## Главное

Датасет можно брать в обучение, но случайное разбиение почти наверняка даст завышенную оценку.

В данных 144 313 объявления. На каждое объявление есть текст (`title`, `description`), одно изображение (`image_id`) и итоговая метка `final_label`. Метка состоит из пяти типов корпуса плёночной камеры и `other_unknown`.

Главные проблемы, которые нашлись в EDA:

- `other_unknown` — не один класс, а смесь лотов, аксессуаров, цифровых камер, коробок, плохих фото и случаев без достаточной информации;
- `TLR` редкий: 1 879 строк, 1.3% датасета;
- текст часто даёт сильный сигнал через бренд или модель, но этот сигнал легко превращается в утечку;
- у продавцов есть шаблонные описания, и модель может выучить продавца вместо камеры;
- есть точные и похожие дубли фото;
- `kb` до проверки по фото давал большую часть ошибок на ручном `audit`; после `kb`-override он опускается до 2.6% `AutoErrorRate`, и это ключевой урок этапа.

Поэтому для следующего этапа важнее сначала сделать честное разбиение и контроль утечек, а уже потом сравнивать модели.

## Базовые проверки

В `data_eda.parquet` 144 313 строки. В памяти датафрейм занимает около 137 МБ. Ручная `gold`-разметка есть для 471 строки, `audit` — для 210 строк.

Базовые инварианты сошлись:

| проверка | нарушений |
|---|---:|
| `item_id` уникален | 0 |
| `image_id` уникален | 0 |
| у валидной камеры заполнен `final_body_type` | 0 |
| невалидный объект уходит в `other_unknown` | 0 |
| у валидной камеры `final_label = final_body_type` | 0 |

Пропуски в служебных полях ожидаемые. Например, `final_body_type` пустой для `other_unknown`, а `kb_*` и `llm_*` заполнены только там, где соответствующий источник разметки реально сработал.

## Целевая переменная

`final_label` распределён так:

| класс | строк | доля |
|---|---:|---:|
| `compact_point_and_shoot` | 43 189 | 29.93% |
| `other_unknown` | 27 136 | 18.80% |
| `rangefinder_viewfinder` | 25 073 | 17.37% |

Дисбаланс не катастрофический, но `TLR` точно нельзя терять в общей accuracy. Для него нужны отдельные метрики: хотя бы recall/F1 по классу и macro F1 по всем классам.

`other_unknown` отдельно важен. Это не визуально цельный класс, а мусорная корзина для разных причин отказа:

| `final_object_status` | строк | доля |
|---|---:|---:|
| `valid_single_film_camera` | 117 177 | 81.20% |
| `multi_camera_lot` | 12 439 | 8.62% |
| `digital_camera` | 3 826 | 2.65% |
| `insufficient_info` | 3 310 | 2.29% |
| `accessory_or_part` | 2 731 | 1.89% |
| `not_camera` | 1 552 | 1.08% |
| `box_manual_packaging` | 1 354 | 0.94% |
| `film_or_consumable` | 1 287 | 0.89% |
| `conflicting_evidence` | 609 | 0.42% |
| `image_unavailable` | 28 | 0.02% |

Отсюда нормальная постановка для модели: сначала понять, что это одиночная валидная плёночная камера, и только потом выбирать тип корпуса.

## Откуда пришли метки

Финальная метка собиралась из нескольких источников:

| источник | строк | доля |
|---|---:|---:|
| `llm` | 88 531 | 61.35% |
| `kb` | 48 774 | 33.80% |
| `kb_overridden` | 6 403 | 4.44% |
| `human` | 471 | 0.33% |
| `abstain` | 134 | 0.09% |

`kb` — это справочник по моделям. Он полезный, но опасный для оценки: если одна и та же модель встречается и в обучении, и в тесте, модель может просто выучить название из текста. Тогда метрика будет красивой, но честного обобщения не будет.

По `audit` видно, где была основная боль и как её закрыл `kb`-override:

| срез | N | авто-заполнено | правильно | ошибок | `CorrectAutofillRate` | `AutoErrorRate` |
|---|---:|---:|---:|---:|---:|---:|
| финальная логика на `audit` (после `kb`-override) | 210 | 158 | 153 | 5 | 72.86% | 3.16% |
| только `llm`-часть на `audit` | 116 | 81 | 78 | 3 | 67.24% | 3.70% |
| `kb` принят на `audit` | 77 | 77 | 75 | 2 | 97.40% | 2.60% |
| `kb_overridden` на `audit` | 17 | 0 | 0 | 0 | — | — |

Бизнес-ограничение из предыдущего этапа — `AutoErrorRate <= 5%`. До проверки `kb` по фото текстовый справочник давал на `audit` около 17% ошибок — именно это мотивировало стейдж `verify_kb`. После override (он уже в финальном датасете) `AutoErrorRate` на `audit` равен 3.16% при `CorrectAutofillRate` 72.86%, то есть ограничение выполняется. Оговорка: выборка 210 строк мала, Wilson CI на 5 ошибках из 158 примерно 1.3–7.2%, верхняя граница задевает 5% — для уверенного вывода нужен аудит на 500–1000 строк.

`gold` для финальной оценки не годится: финальная метка для gold-строк по построению равна gold-метке (приоритет `gold > kb > llm`), поэтому `AutoErrorRate = 0%` на `gold` — это тождество, а не оценка качества. Информативна только независимая сверка `kb_label` или `llm` против `gold_label`.

## Текст

Тексты короткие. Для `title + description` p99 грубой оценки — около 443 токенов. Лимита 256--512 токенов должно хватить почти для всех объявлений.

Сама длина текста по классам близкая, поэтому длина не выглядит сильным признаком. Гораздо важнее, что именно написано: модель, бренд, слова продавца, лот или аксессуар.

Дубли по тексту:

| ключ | уникальных | групп с размером >= 2 | строк в таких группах | максимальная группа | доля строк |
|---|---:|---:|---:|---:|---:|
| `title_norm` | 62 596 | 9 169 | 90 886 | 7 461 | 62.98% |
| `desc_norm` | 130 810 | 3 105 | 16 608 | 488 | 11.51% |
| `title + description` | 140 489 | 1 750 | 5 574 | 69 | 3.86% |

Самые большие группы по заголовку — это не настоящие дубли, а слишком общие названия:

| `title_norm` | строк | почему это плохо |
|---|---:|---|
| `пленочный фотоаппарат` | 7 461 | внутри разные классы, один заголовок не решает задачу |
| `фотоаппарат` | 1 304 | слишком общий текст |
| `фотоаппарат зенит` | 1 114 | уже есть сигнал на `SLR`, но всё ещё возможны лоты и ошибки |
| `фотоаппарат polaroid 636` | 1 469 | сильный сигнал на `instant`, но встречается `other_unknown` |

Полных дублей `title + description` намного меньше, чем повторяющихся заголовков. Поэтому проблема не в том, что датасет забит копиями одного и того же объявления, а в том, что много объявлений называются слишком общо.

Примеры текстовых сигналов по классам:

| класс | примеры текста / моделей | комментарий |
|---|---|---|
| `SLR` | `Зенит`, `Киев`, `Nikon FM2n`, `Canon EOS` | бренд сам по себе не всегда хватает, нужна модель или фото |
| `TLR` | `Любитель`, `Rolleiflex`, `Yashica Mat` | редкий класс, но с сильным визуальным признаком |
| `rangefinder_viewfinder` | `ФЭД-2`, `Зоркий 4`, `Leica III` | советские модели хорошо ловятся справочником |
| `compact_point_and_shoot` | `Olympus mju`, `superzoom`, `fino`, просто `Фотоаппарат` | много бедных заголовков, фото часто важнее текста |
| `instant` | `Polaroid 636`, `Instax mini 12`, `Instax mini 11` | самый понятный текстовый сигнал |
| `other_unknown` | `Фотоаппараты`, лот, коробка, чехол, картриджи | это не один класс, а разные причины отказа |

Лексика специфична неравномерно. Для `instant`, советских `SLR` и `rangefinder_viewfinder` текст часто сильный: названия моделей прямо указывают на класс. Для `compact_point_and_shoot` и общих заголовков вроде `пленочный фотоаппарат` текста мало, и без фото легко ошибиться.

Отдельно всплыли шаблоны продавцов. В списке слов, связанных с классом, наверху иногда оказываются не признаки камеры, а стиль конкретного продавца: юридические дисклеймеры, одинаковые фразы, хеши, подмена кириллицы латиницей (`испpавно`, `дoлго`, `радовaть`). Точную долю таких странных написаний я здесь не считал, но для обучения это всё равно важно: текст надо нормализовать, а качество проверять на разбиении по `user_id`.

Предобученную текстовую модель использовать можно, но только как часть решения. Одного текста недостаточно: на общих заголовках класс часто нельзя восстановить. Плюс нужно проверять, не выучила ли модель названия популярных моделей и шаблоны продавцов вместо признаков камеры.

## Фото

С технической стороны фото чистые:

- 144 313 jpg-файла;
- битых файлов нет;
- все изображения в RGB;
- EXIF пустой;
- ширина, высота и размер файла без больших выбросов.

Для подготовки изображений достаточно обычного изменения размера и обрезки кадра. Отдельно чистить EXIF не нужно.

Дубли фото есть:

| тип дубля | групп | фото |
|---|---:|---:|
| точные дубли по `sha256` | 1 217 | 2 952 |
| похожие дубли по `dhash` | 1 560 | 3 959 |

Их надо учитывать при разбиении. Иначе одна и та же или почти одинаковая фотография может попасть и в обучение, и в тест.

По фото не всегда можно однозначно определить ответ. У основных классов есть понятные визуальные маркеры, но хватает спорных случаев.

| класс | визуальный признак |
|---|---|
| `SLR` | призма сверху, один объектив по центру |
| `TLR` | две линзы одна над другой |
| `rangefinder_viewfinder` | плоский корпус, отдельное окно видоискателя |
| `compact_point_and_shoot` | небольшой корпус, встроенная вспышка, простая форма |
| `instant` | широкий корпус, слот выхода фото |
| `other_unknown` | общего признака нет: лот, коробка, аксессуар, расходник, цифровая камера |

`rangefinder_viewfinder` самый смешанный визуально: туда попадают дальномерные, шкальные и простые видоискательные камеры. Это нормально для текущей схемы, потому что по одному фото без знания модели их часто трудно развести.

`other_unknown` визуально ещё хуже: у него нет общего вида. В одном классе лежат лоты, коробки, цифровые камеры, аксессуары, расходники и плохие фото. В таких случаях лучше отказ в `other_unknown`, а не угадывание одного из пяти типов корпуса.

`kb_overridden` показал самые полезные ошибки: текст говорит про камеру, а на фото лот, коробка, чехол, картриджи или аксессуары. Такие примеры лучше держать отдельно для проверки модели.

По разрешению: финальные фото уже приведены к обычным размерам Авито, объект на них в целом виден. Для первой модели я бы начинал с 384x384 или похожего размера, а 224x224 проверял отдельно. Для `TLR` и `SLR` признаки крупные, но у `rangefinder_viewfinder` и `compact` мелкие детали могут потеряться на слишком маленьком размере.

По визуальным признакам дисбаланс тоже есть. `TLR` редкий, `rangefinder_viewfinder` смешанный, а `other_unknown` не имеет одного общего вида. Ещё есть сдвиг по брендам: японские бренды часто оказываются компактами, а не зеркалками.

Аугментации, которые выглядят безопасно:

- небольшой crop / resize;
- небольшой поворот;
- изменение яркости и контраста;
- лёгкий blur / JPEG-компрессия;
- небольшое изменение масштаба.

Вертикальный flip брать не надо: такие фото не похожи на реальные объявления. Горизонтальный flip тоже под вопросом: тип корпуса не меняется, но надписи, кнопки и хват камеры становятся неестественными. Я бы сначала обучал без него, а потом проверял отдельным экспериментом.

Синтетические данные для этой задачи не выглядят полезными. Реалистично сгенерировать корпуса старых камер сложно, а простая синтетика даст не тот домен. Более практичный вариант — использовать открытые каталоги камер или магазинные фото для предобучения/дообучения image encoder, а потом обязательно проверять на фото Авито. У каталожных фото фон и качество другие, поэтому без проверки на реальных объявлениях им доверять нельзя.

## Бренды, модели и подгруппы

Бренд и класс камеры не совпадают.

Самый показательный пример — группа Nikon/Canon/Pentax/Minolta/Olympus: 27 801 строка, из них около 60% относятся к `compact_point_and_shoot`, а `SLR` занимает только 25%. Эти бренды выпускали и зеркалки, и мыльницы. Поэтому правило `Nikon/Canon/Olympus = SLR` ломается.

Советские бренды проще для справочника:

- Зенит/Киев чаще дают `SLR`;
- ФЭД/Зоркий чаще дают `rangefinder_viewfinder`;
- `Instax` и `Polaroid` в основном уходят в `instant`.

Но это тоже источник утечки. Если популярная модель попадает и в обучение, и в тест, модель может выучить название, а не конструкцию. Это надо проверять маскированием части названий в заголовке и отдельной оценкой на популярных `kb_model`.

Отдельные спорные случаи уже видны:

- `Olympus IS`: 499 строк, из них 329 `compact`, 126 `SLR`, 44 `other_unknown`. Серия пограничная: внешне похожа на большую мыльницу/bridge-камеру, поэтому её легко разнести по разным классам.
- Ложные срабатывания регулярных правил на числа: пример `Рюкзак империи 1943`, который поймался правилом `зоркий 4`.
- `ФЭД-2 комплект`: слово `комплект` иногда означает лот, а иногда одну камеру с аксессуарами.

## Продавцы

Уникальных `user_id`: 94 305. Большинство продавцов встречается редко: медиана — 1 объявление, p95 — 2, p99 — 7. Но хвост тяжёлый: самый крупный продавец даёт 1 375 объявлений.

Топ-3 продавца дают 3 311 объявлений, это 2.3% датасета. Если убрать топ-500 продавцов, уйдёт 20.66% строк, но баланс классов почти не меняется: TVD = 0.0340. Значит, разбиение по `user_id` не должно сильно ломать распределение классов.

Некоторые продавцы почти полностью сидят в одном классе:

- `b68008d3...` — 98.2% `compact`;
- `85acab92...` — 95.42% `compact`;
- есть продавцы с большой долей `other_unknown`: `cc70cfba...`, `a142b054...`, `9c5dbf1f...`.

`user_id` нельзя давать модели как признак. Он нужен только для разбиения, проверки утечек и анализа ошибок.

## Что делать для обучения

Разбиение:

- основной вариант — `GroupKFold` по `user_id`;
- точные и похожие фото (`sha256`, `dhash`) держать в одной части;
- одинаковые `title_norm` держать вместе или хотя бы отдельно считать качество на таких группах;
- популярные `kb_model` контролировать отдельно.

Метрики:

- не ограничиваться accuracy;
- считать macro F1;
- отдельно смотреть `TLR`;
- отдельно смотреть группы брендов и моделей;
- отдельно смотреть ошибки по источнику метки: `kb`, `llm`, `kb_overridden`.

Модель:

- одной текстовой модели мало;
- фото обязательно нужно для бедных заголовков и проверки `kb`;
- `other_unknown` лучше делать как отдельный первый шаг: валидная одиночная плёночная камера или нет;
- для `TLR` можно попробовать веса классов;
- для крупных продавцов можно проверить понижающий вес вроде `1/sqrt(n_listings_per_user)`.

## Ограничения EDA

1. В данных нет времени. Нельзя сделать разбиение по времени и проверить сдвиг свежих объявлений относительно старых.
2. EXIF пустой у всех фото. По нему нельзя восстановить дату или устройство.
3. Неизвестно, как именно отбирались объявления в дамп: все подряд, активные, архивные, прошедшие модерацию.
4. Метрики финальной логики на `gold` не являются оценкой качества: для gold-строк финальная метка по построению равна gold-метке, поэтому `AutoErrorRate = 0%` — это тождество, а не качество.
5. Частотные слова по классам не являются независимой проверкой: `kb` и `llm` тоже использовали `title + description`.
6. Защита от утечек пока проверена только анализом, а не обучением модели.
7. `other_unknown` слишком разнородный; если бизнесу нужны разные действия для лотов, аксессуаров и цифровых камер, это надо анализировать отдельно.

## Итог

Данных достаточно для обучения мультимодальной модели, но главный риск сейчас — не архитектура, а завышенная оценка из-за утечек.

Минимальный план на следующий этап:

1. собрать разбиение по `user_id` с контролем `sha256/dhash` и `title_norm`;
2. обучить базовую модель текст+фото;
3. считать macro F1 и бизнес-метрики `CorrectAutofillRate` / `AutoErrorRate`;
4. отдельно разобрать ошибки `kb`, потому что именно там сейчас основная доля неправильных автозаполнений;
5. проверить, сколько ошибок убирается отказом в `other_unknown` при низкой уверенности.
