# Обучение модели и её оценка

Проект: автоматическое определение типа корпуса плёночной камеры по объявлению Авито.  
Категория: Электроника / Фототехника / Плёночные фотоаппараты.  
Целевой атрибут: `film_camera_body_type`.  
Папка этапа: `training/`.

На этом этапе я обучал модель, которая по заголовку, описанию и главному фото возвращает тип корпуса камеры. Если по объявлению безопасно выбрать класс нельзя, модель отдаёт `other_unknown`.

Большую нейросеть я не дообучал. На это нет GPU-бюджета, а для проекта нужна модель, которую можно обслуживать без дорогого железа. Поэтому я сделал дистилляцию: Gemini дал метки, готовые модели один раз посчитали признаки, а сверху обучалась лёгкая `LogisticRegression`. GPU понадобился только для эмбеддингов на Kaggle, все остальные прогоны шли локально на CPU.

## Главное

Лучший результат дала `LogisticRegression` на шести классах. В неё я подаю четыре блока признаков:

```text
title + description -> TF-IDF char_wb
text                -> Qwen3 text embedding
image               -> DINOv3 image embedding
image               -> PE-Core image embedding

[all features] -> LogisticRegression(C=1.0, class_weight=None) -> 6 probabilities
```

Дальше я называю этот вариант `lrgrid__c1.0__none`. Его я выбрал по val на 19 195 строках. Ручной audit на 210 строках оставил только для финальной проверки, а не для выбора между близкими конфигами.

| что | значение |
|---|---:|
| строк всего | 144 313 |
| split | train 103 039 / val 19 195 / test 22 079 |
| ручной audit | 210 строк, только в test |
| финальные признаки | TF-IDF 50k + Qwen3 1024 + DINOv3 384 + PE-Core 1024 |
| итоговая размерность | 52 432 |
| голова | `LogisticRegression(C=1.0, class_weight=None)` |
| порог отказа | `tau = 0.0`, принимаю все предсказания основных классов |
| val: CAR / AER / AER_hi | 0.787 / 0.041 / 0.044 |
| test по Gemini: CAR / AER / AER_hi | 0.835 / 0.037 / 0.040 |
| test по человеку: CAR / AER / AER_hi | 0.748 / 0.025 / 0.062 |

На val модель проходит ограничение сразу, без дополнительного порога: среди автозаполненных строк ошибка 4.1%, с запасом - 4.4%. Поэтому отдельный отказ по уверенности почти не нужен.

На ручном audit получилось 161 автозаполнение: 157 правильных и 4 ошибки. По точке это 2.5%, то есть ниже нужных 5%. Но 210 строк - маленькая проверка. Если считать с запасом, получается 6.2%. Чтобы запас тоже прошёл 5%, на таком размере надо иметь не больше двух ошибок.

Из-за этого я не выбирал модель по audit. Там один-два примера меняют вывод сильнее, чем многие правки модели. Модель выбиралась на val, audit остался проверкой на человеке.

## Постановка и подход

Это задача заполнения параметра товара. По карточке надо понять, какой у камеры тип корпуса.

Текст часто даёт модель: `Зенит`, `ФЭД`, `Любитель`, `Instax`, `Olympus mju`. Фото помогает, когда заголовок бедный, модель написана с ошибкой или в объявлении вообще не одна камера, а лот, коробка, аксессуар или цифровая камера.

Сервис должен держать минимум 1 rps, поэтому я не дообучал большую мультимодальную модель. Я взял готовые признаки: Qwen3 по тексту, DINOv3 и PE-Core по фото, плюс TF-IDF по тексту. Сверху обучается `LogisticRegression`.

Классы модели:

| класс | смысл |
|---|---|
| `SLR` | однообъективная зеркальная плёночная камера |
| `TLR` | двухобъективная камера |
| `rangefinder_viewfinder` | дальномерная, шкальная или видоискательная камера |
| `compact_point_and_shoot` | компактная автоматическая камера |
| `instant` | Polaroid / Instax / моментальная печать |
| `other_unknown` | не заполнять: не камера, лот, аксессуар, цифровая камера, мало данных или случай вне схемы |

В этой задаче пустое поле лучше, чем неверный тип камеры.

## Метрика

Accuracy тут плохо отражает задачу. Она не различает две ситуации: модель отказалась или модель заполнила поле неправильно. Для каталога это разные вещи: неправильный тип корпуса отправит объявление не в тот фильтр, а отказ просто оставит поле пустым.

Обозначения:

```text
N = все объявления в контрольной выборке
A = объявления, где модель вернула один из 5 основных классов
C = объявления из A, где класс выбран правильно
W = объявления из A, где класс выбран ошибочно

CorrectAutofillRate = C / N
AutoErrorRate = W / A
AutoErrorRate_hi = верхняя оценка ошибки W / A
```

Модель выбиралась так: больше правильных автозаполнений, но не больше 5% ошибок среди тех строк, где модель решила заполнить поле.

Порог и конфиг подбирались на val. Audit я использовал только в конце.

## Валидация без утечек

Главный риск здесь - завысить качество. В данных много повторов: один продавец выкладывает похожие объявления, фото повторяются, заголовки часто шаблонные. При случайном split модель может выучить не камеру, а продавца или шаблон.

По времени я не делил: нормальной даты объявления в данных нет, EXIF тоже пустой. Поэтому я защищался от другого риска - повторов одного и того же содержимого.

Split `split_v1` строится один раз и дальше заморожен:

```text
связи: user_id, sha256 фото, dhash фото, text_hash
как делю: связанные строки собираются в одну группу
правило: группа целиком попадает только в train, val или test
```

Итоговое разбиение:

| split | строк | доля | leakage-групп | TLR строк |
|---|---:|---:|---:|---:|
| train | 103 039 | 71.4% | 73 927 | 1 049 |
| val | 19 195 | 13.3% | 18 846 | 188 |
| test | 22 079 | 15.3% | 678 | 642 |

Все 210 audit-строк и 471 gold-строка принудительно лежат в test. Пересечений между split по `user_id`, `sha256`, `dhash` и `text_hash` - 0.

Из-за этого test получился неровным: туда вместе с audit и gold подтянулись связанные с ними группы. Поэтому в test меньше групп и больше TLR, чем было бы при обычном случайном split. Я оставил так, потому что для оценки важнее не смешать связанные объявления между train и test.

Таргет в признаки не попадает. В модель не подаются `label_source`, `kb_model`, сырые ответы Gemini и служебные колонки разметки. TF-IDF и скейлеры обучаются только на train. Все merge с эмбеддингами проверяются как one-to-one, а prediction contract проверяет вероятности, уверенность и выбранный класс.

Для стекинга и acceptor я сделал то же самое: вторая модель обучалась только на предсказаниях, полученных без просмотра этой строки и её группы.

Такой val не идеально повторяет будущий поток. Новые продавцы и новые модели камер всё равно появятся. Но для сравнения моделей этот split безопаснее случайного: похожие объявления разведены по разным частям, и модель не получает лёгкий путь через повторы.

## Бейзлайн

Первый бейзлайн - справочник `бренд + модель -> тип корпуса`. Он хорошо работает, когда в тексте явно написана модель камеры, но не закрывает бедные заголовки, лоты и аксессуары.

На ручном audit справочник автозаполняет 77 строк из 210 и правильно заполняет 75:

```text
A = 77
C = 75
W = 2
CorrectAutofillRate = 75 / 210 = 0.357
AutoErrorRate = 2 / 77 = 0.026
```

Справочник точный, но срабатывает редко: CAR 35.7%. Поэтому модель должна была заполнить больше объявлений и не выйти за лимит ошибок.

Первый ML-вариант `TF-IDF + DINOv3 -> LogReg` уже дал около 76% CAR на val и 73.8% на audit. Дальше я добавлял по одному блоку: Qwen3, PE-Core, другие головы и отдельные проверки отказа.

## Лестница моделей

Все основные эксперименты запускались через `src/train.py`, конфигами из `src/experiments.py`, и логировались в MLflow. Сначала я проверял отдельные модальности, потом fusion, потом головы и отдельные попытки пробить потолок.

| модель | что проверял | val CAR | audit CAR | audit AER_hi |
|---|---|---:|---:|---:|
| KB heuristic | простой справочник моделей | - | 0.357 | - |
| TF-IDF only | хватает ли текста | 0.296 | 0.310 | 0.122 |
| DINOv3 only | хватает ли фото | 0.312 | 0.348 | 0.092 |
| Qwen3 only | текстовый эмбеддинг без TF-IDF | 0.375 | 0.405 | 0.095 |
| TF-IDF + DINOv3 | первый сильный текст+фото | 0.762 | 0.738 | 0.079 |
| TF-IDF + Qwen3 + DINOv3 | лексика + смысл текста + фото | 0.775 | 0.748 | 0.085 |
| + PE-Core | ещё один сигнал по фото | 0.786 | 0.748 | 0.078 |
| + PE-Core, `class_weight=None` | лучший вариант головы | 0.787 | 0.748 | 0.062 |

По отдельности текст и фото дают мало автозаполнений. Лучший результат появился после склейки: TF-IDF ловит названия моделей и короткие фразы, Qwen3 добавляет смысл текста, DINOv3 и PE-Core помогают по фото.

Qwen3 сам по себе оказался слабее TF-IDF: названия старых камер лучше ловятся символьными n-граммами. Но вместе с TF-IDF он помог. PE-Core тоже дал прирост, причём не через prompt-similarity, а через сырой image embedding.

Бустинги лучше совпадали с Gemini, но хуже проходили ручной audit. Поэтому я не выбирал голову только по F1 против Gemini: такая модель лучше повторяет учителя, но не обязательно ближе к человеку.

## Чемпион

Финальная выбранная конфигурация:

```text
name: lrgrid__c1.0__none
features: tfidf + qwen3 + dinov3 + pe
head: LogisticRegression
C: 1.0
class_weight: None
tau: 0.0
```

Конфиг выбран по val. `C=1.0` дал лучший CAR среди близких вариантов. `class_weight=None` оказался лучше `balanced`.

`C=3.0` выглядел чуть лучше на audit, но на val не выигрывал. Я не стал менять чемпиона из-за пары ручных строк.

Порог `tau = 0.0`: модель уже проходит val без дополнительного отказа.

После выбора конфига я обучил финальную модель на `train + val` через `src/final_refit.py`. Архитектура и порог не менялись. Test и audit остались только для проверки. Бандл и meta-файл лежат в `final_model/`.

## Анализ ошибок

Ошибки автозаполнения я делю на два типа:

| тип ошибки | смысл | пример |
|---|---|---|
| `should_abstain` | модель поставила основной класс, а надо было отказаться в `other_unknown` | лот, аксессуар, кинокамера, цифровая камера |
| `wrong_type` | это камера, но выбран не тот тип корпуса | rangefinder перепутан с compact, SLR с rangefinder |

У чемпиона на proxy-тесте 22k:

```text
A = 19169
W = 728
should_abstain = 482, 66% ошибок
wrong_type = 246, 34% ошибок
```

На ручном audit:

```text
A = 161
W = 4
should_abstain = 3
wrong_type = 1
```

Чаще всего проблема не в типе камеры, а в самом объекте объявления:

- `Камера Красногорск-3 рабочая` - кинокамера, но модель тянет в SLR;
- `Olympus OM system OM-5` - современная цифровая камера в неправильной категории;
- `Видоискатель оптический ... на фотоаппарат` - аксессуар, а не камера;
- `Фотоаппараты пленочные Olympus` - лот, но модель пытается выбрать один тип.

Ошибок между типами меньше. Обычно это спор между compact и rangefinder или редкая модель:

- `Konica C35 EF` - пограничные compact/rangefinder случаи;
- `Olympus IS-200` - пограничная серия между SLR и compact;
- `Contax G1` и похожие редкие модели - без знания конкретной модели легко ошибиться.

Многие ошибки уверенные. Название камеры перевешивает слова вроде `лот`, `ассортимент`, `видоискатель`, `кино`. Поэтому порог, regex и отдельная модель отказа почти не помогли.

## Что выучила модель

Я проверил коэффициенты TF-IDF у logreg. В топе оказались обычные слова и куски названий камер, а не служебные поля:

| класс | сильные текстовые куски | почему это нормально |
|---|---|---|
| `TLR` | `люб`, `любит`, `бител` | `Любитель` - частая советская TLR |
| `rangefinder_viewfinder` | `фэд`, `смена`, `зорк` | ФЭД, Смена, Зоркий |
| `instant` | `inst`, `polaroid`, `mini 11` | Instax / Polaroid |
| `SLR` | `зен`, `zenit`, `is-200` | Зенит и SLR-гибриды |
| `compact_point_and_shoot` | `zoom`, `mju`, `fino` | компактные авто-камеры |
| `other_unknown` | `фотоаппараты`, `шт`, `оба`, `лот` | много объектов или отказ |

Это нормальный набор признаков для задачи. `label_source`, `kb_model`, `user_id` и сырые ответы Gemini в модель не подавались. По весам не видно одного служебного шортката: модель использует и TF-IDF, и эмбеддинги.

## Что я пробовал после чемпиона

После выбора logreg я проверил, можно ли улучшить отказ, исправить тип или использовать спор между текстом и фото. Эти прогоны не попали в финал, но объясняют, почему я оставил простую голову.

| рычаг | что хотел исправить | что произошло |
|---|---|---|
| каскад `камера/не камера -> тип` | сначала отсеять лоты и аксессуары | ошибок отказа стало меньше, но ошибок типа стало больше |
| пороги по классам | можно ли по-разному доверять классам | модель уже проходит val без порога; новые пороги только убирают верные ответы |
| acceptor | отдельная модель “верить или отказаться” | на val срезал несколько ошибок, но на ручном audit ничего не поменял |
| hard-negative override | руками зарезать лоты, аксессуары, цифровые камеры | маркеры контекстны: `видоискатель`, `вспышка`, `комплект` часто встречаются у реальных камер |
| подтипы `other_unknown` | разделить лоты, аксессуары, цифру и кино | правила для подтипов получились шумными, итоговый `other_unknown` стал слабее |
| веса по источнику метки | меньше доверять Gemini-строкам | стало хуже: LLM-строки содержат не только шум, но и много сложных примеров |
| веса блоков | сильнее или слабее доверять TF-IDF, Qwen, DINO, PE | на val почти ничего не меняется, а audit прыгает на 1-2 строки |
| title/description split | отделить надёжный title от шумного description | не лучше чемпиона, audit хуже |
| расширение словаря | добавить редкие слова и фразы | лучше совпадает с Gemini, но на ручном audit не помогает |
| OOF modality-stacking | можно ли доверять модели меньше, когда текст и фото спорят | ошибок стало меньше, но правильных автозаполнений тоже меньше; для моей цели это не выигрыш |
| kNN | искать похожие объявления в train | чинит 31 ошибку типа, но ломает около 96 верных ответов |
| возврат отказов | можно ли часть `other_unknown` вернуть в основные классы | val немного вырос, но ошибки подошли к лимиту; на ручном audit прирост не подтвердился |

После этих проверок стало понятно, что усложнение головы не даёт выигрыша на ручном audit.

## Почему я остановился

После бустингов, расширения словаря, стекинга и возврата отказов картина повторялась: на Gemini-метках лучше, на ручном audit - нет. Поэтому я не выбирал модель по proxy/F1. Более мощная голова здесь чаще лучше повторяет Gemini, а не человека.

На этом я остановился. У текущей модели уже 95.9% верных автозаполнений на val, а ошибка среди автозаполнений ниже 5%. Поэтому пороги, acceptor и другие механизмы отказа в основном убирают правильные ответы.

В рамках этого этапа новых ручных меток нет, а эмбеддинги уже посчитаны. Значит дальше я не могу честно доказать улучшение на человеке: audit маленький, и близкие конфиги отличаются там на одну-две строки.

## Что это значит для продукта

Для проекта модель можно брать как вариант с упором на качество. На ручном audit она правильно заполняет 74.8% строк. Среди автозаполненных строк ошибка 2.5%. Основные промахи понятны: лоты, аксессуары, цифровые камеры, кинокамеры и граница `compact_point_and_shoot` / `rangefinder_viewfinder`.

При этом 210 строк мало, чтобы строго обещать ошибку ниже 5% на любом новом потоке. По точке модель проходит, но запас по ручной проверке небольшой.

Скорость ответа здесь ещё не была целью. Logreg-голова дешёвая, но Qwen3, DINOv3 и PE-Core могут быть тяжёлыми, если считать их онлайн на CPU. Это надо будет проверить уже в сервисном этапе.

## Структура папки

```text
training/
|-- README.md
|-- notebooks/          Kaggle-ноутбуки для эмбеддингов
|-- src/                обучение, конфиги, финальный refit и analysis-скрипты
|-- validation/         split, evaluator и prediction contract
|-- tracking/           MLflow
|-- reports/            summary и отчёты по ошибкам/экспериментам
|-- final_model/        финальный joblib-бандл и meta.yaml
`-- artifacts/          эмбеддинги, предсказания и модели; в git не кладётся
```

`artifacts/` не должен жить в git целиком: там тяжёлые parquet, предсказания и joblib-бандлы. В git достаточно держать код, отчёты, split manifest и meta-контракт финальной модели.

## Как запустить

Из корня репозитория:

```bash
pip install -r requirements.txt
```

Один раз извлечь эмбеддинги на Kaggle GPU через ноутбуки:

```text
training/notebooks/extract_text_qwen3.ipynb
training/notebooks/extract_dinov3.ipynb
training/notebooks/extract_pe_core.ipynb
```

Скачанные parquet кладутся в:

```text
training/artifacts/embeddings/
```

Посмотреть каталог экспериментов:

```bash
python training/src/train.py --list
```

Запустить текущий список `TO_RUN` из `src/experiments.py`:

```bash
python training/src/train.py
```

Запустить один конкретный эксперимент:

```bash
python training/src/train.py lrgrid__c1.0__none
```

Запустить все конфиги из каталога:

```bash
python training/src/train.py --all
```

Открыть MLflow UI:

```bash
bash training/tracking/ui.sh
```

После этого UI доступен локально:

```text
http://127.0.0.1:5000
```

MLflow пишет в локальный sqlite store. Сам store в git не нужен, потому что для отчёта экспортируется `reports/experiments_summary.csv`.

Перегенерировать основные отчёты анализа:

```bash
python training/src/analysis/error_analysis.py
python training/src/analysis/threshold_analysis.py
python training/src/analysis/acceptor_analysis.py
python training/src/analysis/stack_analysis.py
python training/src/analysis/business_policy_analysis.py
```

Собрать финальную модель после выбора чемпиона:

```bash
python training/src/final_refit.py
```

Загрузить финальный бандл головы (лежит в git):

```python
import joblib

bundle = joblib.load('training/final_model/tfidf_qwen3_dinov3_pe_logreg_reg1_0_unweighted_final_pipeline.joblib')
clf = bundle['classifier']
tau = bundle['tau']
labels = bundle['labels']
```

Точный порядок фич, названия предобученных энкодеров и размерности зафиксированы в `final_model/*_meta.yaml`.

## Что зафиксировано

К концу этапа я фиксирую `split_v1`, evaluator, метрику, 6 классов, чемпиона `lrgrid__c1.0__none` и порог `tau = 0.0`. Все модели сравнивались на одном и том же split. Audit не использовался для выбора гиперпараметров.

## Итог

Я начал со справочника и простого `TF-IDF + DINOv3 -> LogReg`, потом добавил Qwen3, PE-Core и проверил другие головы. Лучшим остался простой вариант: `LogisticRegression` поверх сильных замороженных признаков.

Финальная модель проходит бизнес-метрику по точке на ручном audit: CAR 74.8%, AER 2.5%. На val она проходит ограничение и с запасом: AER 4.1%, AER_hi 4.4%. На ручном audit запас не доказывается из-за размера выборки: 4 ошибки на 161 автозаполнение дают AER_hi 6.2%.

Я не стал подбирать модель по этим 210 строкам. Близкие конфиги там отличаются на одну-две карточки, а на val выигрыша не дают. Поэтому финальным вариантом оставляю `lrgrid__c1.0__none`.
